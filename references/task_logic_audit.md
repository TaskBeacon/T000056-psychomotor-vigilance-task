# Psychomotor Vigilance Task Logic Audit

This audit is derived from the selected literature before task implementation. It does not use template trial code as protocol evidence.

## 1. Paradigm Intent

- Task: Psychomotor Vigilance Task (PVT), standard visual reaction-time variant.
- Primary construct: sustained attention / behavioral alertness.
- Manipulated factors: no experimental condition manipulation in the baseline variant; unpredictable response-stimulus interval produces time-on-task demand.
- Dependent measures: reaction time, median and mean RT, lapses (`RT > 500 ms`), false starts (responses before target or target RT `< 100 ms`), no-response events, reciprocal response speed, and time-on-task trends.
- Key citations: `W2008161183`, `W2142478512`, `W143922047`, and `W2098748797`.

## 2. Block/Trial Workflow

### Block Structure

- Total blocks: 1 uninterrupted vigilance block.
- Trials per block: 90 stimulus-response events in the human profile; QA and simulation use shortened event counts while preserving all state semantics.
- Randomization/counterbalancing: each event receives an independently sampled 2-10 s response-stimulus interval through the PsyFlow duration-range path.
- Condition weight policy: one `standard` condition; no weights are required and `task.condition_weights` is omitted.
- Condition generation method: built-in `BlockUnit.generate_conditions(...)` with one label. Custom condition generation is unnecessary because the only varying value is protocol timing jitter handled by `StimUnit`.
- Generated condition data shape: scalar string `standard` passed to `run_trial()`.
- Runtime-generated trial values: the 2-10 s interval is sampled by `StimUnit.capture_response(...)`. The experimental condition sequence is constant, and timing randomness is independent of condition generation.

### Trial State Machine

1. Response-stimulus interval:
   - Onset trigger: `isi_onset`.
   - Stimuli shown: blank black screen.
   - Valid keys: `space`.
   - Timeout behavior: after a randomly sampled 2-10 s interval with no keypress, show the target.
   - Response behavior: a keypress is a false start; record it and end the event without presenting a target.
   - Next state: target counter after timeout, otherwise next event.
2. Target counter:
   - Onset trigger: `target_onset`.
   - Stimuli shown: centered red five-digit millisecond counter beginning at `00000` and updating while visible.
   - Valid keys: `space`.
   - Timeout behavior: after 65 s, record `no_response` and advance.
   - Response behavior: record RT; RT `< 100 ms` is classified as a false start, RT `> 500 ms` as a lapse, otherwise a valid non-lapse response.
   - Next state: RT feedback for responses at or above 100 ms; otherwise next event.
3. RT feedback:
   - Onset trigger: `feedback_onset`.
   - Stimuli shown: the measured RT in integer milliseconds at screen center.
   - Valid keys: none.
   - Timeout behavior: close after 500 ms.
   - Next state: next event's response-stimulus interval.

## 3. Condition Semantics

- Condition ID: `standard`.
- Participant-facing meaning: an unpredictable wait followed by a red millisecond counter requiring an immediate response.
- Concrete stimulus realization: blank black screen during the interval, then a centered red five-digit counter.
- Outcome rules: pre-target response or target RT `< 100 ms` is a false start; no target response within 65 s is `no_response`; RT `> 500 ms` is a lapse.
- Participant-facing text source: Chinese instructions and static feedback templates are defined in `config/*.yaml`; numeric counter content is generated by a task-specific draw wrapper because it changes each frame.
- Auditability rationale: all wording, colors, positions, keys, thresholds, and timing values remain config-defined; only elapsed counter digits are dynamic.
- Localization strategy: language variants replace config text without editing `run_trial.py`; numeric counter behavior is language-neutral.

## 4. Response and Scoring Rules

- Response mapping: `space` records a response in both the interval and target states.
- Response key source: `task.key_list` in each config.
- Missing-response policy: target timeout at 65 s yields `outcome=no_response`, null RT, no feedback, and no lapse classification.
- Correctness logic: PVT has no choice accuracy; a valid response is a target response with RT at or above 100 ms. False starts and no-responses are invalid events.
- Reward/penalty updates: none.
- Running metrics: valid-response count, false-start count, lapse count, no-response count, and mean valid RT are summarized after the block.

## 5. Stimulus Layout Plan

- Screen name: instruction.
- Stimulus IDs shown together: `instruction_text` only.
- Layout anchors: centered at `(0, 0)`.
- Size/spacing: `height=28`, `wrapWidth=900`, black background.
- Readability/overlap checks: one centered text block; SimHei supports Chinese glyphs.
- Rationale: concise instructions minimize pre-task fatigue.

- Screen name: target counter.
- Stimulus IDs shown together: `target_counter` only.
- Layout anchors: centered at `(0, 0)`.
- Size/spacing: monospaced digits, `height=72`, red on black.
- Readability/overlap checks: one five-digit field with stable dimensions.
- Rationale: matches the central LED-style millisecond-counter presentation described for PC-PVT/PVT-192.

- Screen name: RT feedback.
- Stimulus IDs shown together: `rt_feedback` only.
- Layout anchors: centered at `(0, 0)`.
- Size/spacing: `height=56`, red on black.
- Readability/overlap checks: one integer plus `ms`; no concurrent labels.
- Rationale: reproduces the 500 ms post-response RT display.

## 7. Architecture Decisions (Auditability)

- `main.py` runtime flow style: one simple mode-aware flow using PsyFlow setup, one generated block, and explicit summary.
- `utils.py` used: yes.
- Exact purpose: a small draw hook updates the text of the config-created PsychoPy `TextStim` on each draw. It does not own timing, response capture, trial identity, triggers, persistence, or condition scheduling.
- Custom controller used: no.
- Legacy/backward-compatibility fallback logic required: no.
- PsyFlow owns trial IDs, condition scheduling, duration windows, response/timeout events, triggers, and phase data via `set_trial_context(...)` and `StimUnit.to_dict(...)`.

## 8. Inference Log

- Decision: use 90 events instead of terminating the block from a task-local session timer.
- Why inference was required: PC-PVT describes 5- or 10-minute sessions containing approximately 50-100 events, while the TaskBeacon block contract is event-count based.
- Citation-supported rationale: `W2098748797` reports 50-100 stimulus-response events in 5- or 10-minute sessions. Ninety events combined with a mean 6 s interval and 500 ms feedback approximates a standard 10-minute session while retaining PsyFlow-native scheduling.

- Decision: use the space bar rather than mouse buttons.
- Why inference was required: PVT implementations differ in response hardware, and the local task battery standardizes keyboard acquisition.
- Citation-supported rationale: `W2098748797` explicitly treats the response device as an implementation choice while preserving the same visual simple-RT contract.

- Decision: display the dynamic counter as red monospaced text on a black background.
- Why inference was required: the cited hardware uses an LED dot-matrix display, while PsychoPy uses monitor-rendered text.
- Citation-supported rationale: `W2098748797` specifies a four/five-digit millisecond counter; the chosen rendering preserves digits, timing meaning, central placement, high contrast, and stable width.
